## T2-A. Page-body rewriting in Phase 2

**Problem.** Today `curio process --route-file routes.json` accepts route + category + status + scores per page. The page body remains the raw intake capture — Confluence-fetched HTML stripped to markdown, often verbose, sometimes structurally weak. Per `process.md` §"Required proposal outputs" the proposal must include `proposed page body` (synthesized, not captured), with the structured decision section at the top.

**Approach.**
1. Extend the routes.json schema (per-decision) with optional fields:
   - `proposed_body_markdown`: the agent's rewritten body. When present, replaces intake body on apply.
   - `decision_section_markdown`: a structured pre-amble (rationale, scores, route, alternatives) to prepend.
   - `body_rewrite_kind`: `none` | `light_edit` | `full_synthesis` — for audit / metrics.
2. Manifest emit (Phase 1) gains a `body_rewrite_guidance` block in `instructions` that tells the agent when to rewrite vs. keep.
3. Apply path (Phase 2) writes the new body, preserves frontmatter, prepends decision section, records `body_rewrite_kind` in `.proposal.json` dossier.
4. Tests: route-file with `proposed_body_markdown` → applied; route-file without → backwards-compatible behavior preserved.

**Critical files:** `commands/process_intake.rs` (manifest + apply), `proposal.rs` (dossier field), `cli.rs` (no change — flag already there), `tests/process_routing.rs` (new).

**Schema bump:** routes.json from implicit v1 to v2 (additive only).

**Validation:** Apply a sample route-file with `body_rewrite_kind: full_synthesis` against a partner-business intake page; verify the page's body is replaced + decision section prepended + dossier records the kind.

## T2-B. Confluence Review-tree polish

**Problem.** Today `curio sync` mirrors `wiki/review/` and `wiki/staged/` flat under their respective Confluence parents. The Review tree is supposed to be a *human review surface* per `process.md` §"Confluence review behavior" — proposals must surface with their dossier, alternatives, taxonomy mutation, and a clear recommended action. Right now reviewers see a markdown body; they don't see the proposal scores or the merge target unless they read the .proposal.json sidecar (which Confluence doesn't show).

**Approach.**
1. When syncing a `review/` or `staged/` page, render a **proposal header** at the top of the Confluence page: scores table, route/alternatives, merge target if any, taxonomy mutation if any, recommended action, link back to the .md in Git.
2. Per-branch Confluence pages get a generated **child index** with one-line summaries (today already partially supported; tighten the formatting and add proposal-status badges).
3. The pinned reviewer-feedback comment (today's `curio:approve` / `curio:reject` / `curio:rewrite` labels + 👍/👎/❓ reactions) gets clearer wording in the comment body so reviewers know what to click.
4. Stale Confluence prune already exists; verify it covers proposal-header changes too.

**Critical files:** `commands/sync.rs`, `md_to_confluence.rs`, `confluence.rs` (page-body rendering + comment updates).

**Validation:** Sync a partner-business review page to Confluence, visually inspect the rendered header against the spec.

## T2-C. Multi-source synthesis

**Problem.** Today: `curio intake` produces one .md per source; `curio process` produces one decision per .md. The unit of work is a **page**, not a **request**. Per `process.md` §"Stage 2": "An intake request may result in one proposal, multiple proposals, no publishable proposal, or only a rejection / consolidation recommendation." We don't model intake requests at all — sources are isolated.

**Approach.**
1. Add intake-request semantics: a single `curio intake` invocation with multiple sources gets a generated `request_id`, written into the frontmatter of every page it produced.
2. Phase 1 manifest groups intake pages by `request_id`. The agent receives the request as a unit + can decide: 1 proposal, N proposals (split), or merge K sources into 1 proposal.
3. routes.json schema bump (v2 → v3, additive): each entry can name a `merge_into_slug` or a `split_into: [{slug, body}]`. Apply path executes git mv accordingly + records the synthesis decision.
4. Add `kind: Split | Merge` to the existing `ProposalKind` (`Merge` exists today; add `Split`).
5. Tests: 3 sources from one intake batch → 1 merged proposal. 1 source → 2 split proposals.

**Critical files:** `commands/intake.rs` (request_id), `commands/process_intake.rs`, `proposal.rs`, `Frontmatter` (add `request_id`), tests.

**Risks:** invalidates today's 1:1 routing assumption in agent prompts. Mitigation: schema bump is additive; agents that ignore the new fields still produce valid v2 routes.

## T2-D. Embeddings-based overlap

**Problem.** Today `find_peer_overlap` does Jaccard similarity over tokenized words. Misses semantic duplicates that use different vocabulary (e.g. "ODBC connection failure" vs. "DSN driver error"). Per `process.md` §"Overlap rule" semantic overlap is a curation warning signal, and Jaccard is a poor proxy.

**Approach.**
1. Pluggable embeddings provider via `embeddings.rs` trait: `OpenAIEmbeddings` (text-embedding-3-small) and a `LocalCachedEmbeddings` adapter that reads/writes a per-KB `wiki/_admin/embeddings/` cache.
2. Cache embeddings per page on first compute; invalidate on `content_hash` change.
3. Replace `find_peer_overlap` body with cosine similarity; preserve the `OverlapMatch` shape so callers don't change.
4. Config: `overlap.provider: jaccard | openai-embeddings`; default jaccard for backwards compatibility, opt-in via `.curio.yaml`.
5. Tests: snapshot of a known semantic-duplicate pair scoring higher under embeddings than Jaccard.

**Critical files:** `embeddings.rs` (new), `overlap.rs`, `config.rs`.

**Cost:** ~1 embedding per page on first sync. text-embedding-3-small @ ~$0.02 / 1M tokens. For a 100-page KB that's ~$0.0002. Negligible.

## T2-E. Continuous self-sharpening loop

**Problem.** `curio sharpen --prepare` is manual. The design doc requires *continuous* sharpening so KBs improve without operator intervention.

**Approach.**
1. Add `service.runtime` scheduler: emits sharpen prepare / heal prepare jobs at configurable intervals per workspace (cron-string in `wiki/_admin/config.yaml`).
2. Submitted as regular `CurioJobRequest` with `kind: Sharpen` so the existing job audit + execution path covers it.
3. Manifest from the scheduled run is dropped into a Pub/Sub topic (or, locally, written to `wiki/_admin/sharpening-proposals/<timestamp>.json`) for an out-of-band agent to pick up.
4. Tests: scheduler fires at the configured interval, only against `Active` workspaces.

**Critical files:** `service/runtime.rs` (scheduler), `service/types.rs`, `service/server.rs` (introspection endpoint).

## T2-F. Tuning-corpus learning

**Problem.** When the agent rejects similar pages repeatedly (e.g. "low-signal meeting notes from 2024" rejected 12 times this month), there's no infrastructure to codify that as policy and surface it. Today reject reasons go to `wiki/_admin/log.md` as freeform text.

**Approach.**
1. Structured rejection registry: `wiki/_admin/rejections.jsonl` (append-only) with `{slug, reason_code, reason_text, source_kind, dominant_topic, timestamp}`.
2. Periodic analysis (`curio learn --prepare`) emits a manifest of recurring rejection patterns to the agent; the agent proposes harness updates (NORTHSTAR additions, threshold tweaks, automatic reject rules in `_admin/config.yaml`).
3. Agent's response → human-reviewable patches that ship as Review proposals in Confluence.

**Critical files:** `commands/reject.rs` (structured logging), `commands/learn.rs` (new), `_admin/config.yaml` (rules section).

**Note:** depends on T2-C's `request_id` to correlate sources properly.
