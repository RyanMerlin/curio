**First comment** (post within 60 seconds of submitting; this is the founder narrative):

> Author here. Curio started because every knowledge tool I've used indexes documents but none of them editorialize. You drop in raw intake (Confluence pages, files, URLs) and what comes out the other side is exactly what went in — searchable, maybe tagged, but not curated.
>
> Curio is split deliberately: a deterministic Rust substrate (curio-rs) handles git mutations, Confluence v2 API calls, and structural safety; the agent (Claude / Codex / Gemini, via a provider-neutral HARNESS.md contract) handles editorial judgment. The Rust binary makes zero LLM calls. The agent never edits git directly. That split is what makes the rest possible — multi-tenant safety, atomic registry writes, deterministic publish gates.
>
> What's actually shipped in 1.0: two-phase agent-native routing with seven-dimension proposal scoring, multi-source synthesis (one intake can produce one or N proposals after agent-decided merge/split), page-body rewriting (the agent ships curated knowledge objects, not raw captures), Confluence sync that renders the editorial decision data structurally so reviewers see scores / alternatives / taxonomy mutations / merge targets without leaving the page.
>
> What's not shipped yet, in case the comments catch me: embeddings-based overlap (today's overlap is Jaccard token similarity — works, but recalls poorly across vocabulary differences); a continuous self-sharpening scheduler (today `curio sharpen --prepare` is a manual command); a tuning-corpus learning loop (codify recurring rejection reasons into harness policy). All three are designed and planned for v1.1 — see docs/design/2026-05-10-tier2-plan.md in the repo.
>
> The one design choice I'd most want feedback on: the product registry is operator-supplied via wiki/_admin/config.yaml, not baked into the binary. The engine ships zero domain assumptions. That makes Curio genuinely portable across domains (a vendor's product family, an academic discipline's subfields, an FDE team's customer-engagement catalog) — but it also means the first 20 minutes of any deployment is authoring that registry. Curious whether the tradeoff feels right to people who've shipped similar tooling.
>
> Apache 2.0. Tests pass (80/80). Happy to answer questions.

**Why this works:** plain technical voice, specific capabilities, explicit honesty about gaps, one substantive open design question to drive comments.

## Response-plan rubric

When a comment lands within the first 6 hours, classify it before responding:

| Comment shape | Response |
|---|---|
| Substantive technical question about architecture | Reply within 2h. Engage in detail. These are the seed conversations. |
| Specific bug report or repro | Acknowledge in HN/X thread; file a GitHub issue immediately; link it in the reply. |
| Use-case question ("could I use this for X?") | Reply with concrete yes/no + the closest example in the repo. |
| "Why not just use [X tool]?" | Reply once, focused on the specific differentiator. Don't engage further if the OP keeps re-asking. |
| Bait / hostile / no substance | Do not engage. The crowd self-moderates. |
| Praise without substance | Acknowledge briefly, redirect to a substantive thread. |
| Question you don't know the answer to | "Good question — I don't know. Filed as [issue link]." Honesty wins on HN. |

**Hard rule:** do not post a defensive reply. If a critique stings, write the reply in a notes doc, walk away for 30 minutes, then decide whether it's worth posting at all. 90% of the time it isn't.
